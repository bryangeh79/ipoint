## A. Admin eligibility and identity architecture

### A.1 Repository baseline

- `accounts` is the canonical credential identity. It owns normalized email, account status, credential linkage, and sessions (`packages/database/schema/index.ts:283-375`). Account states are `PENDING`, `ACTIVE`, `SUSPENDED`, `LOCKED`, and `ARCHIVED` (`packages/database/schema/index.ts:28-34`).
- `admin_users` is a one-to-one Admin eligibility extension of `accounts`, enforced by `admin_users_account_unique`; it owns Admin display name and `ACTIVE`, `SUSPENDED`, or `ARCHIVED` status (`packages/database/schema/index.ts:46-50,560-574`). It is not a second password identity.
- The shared login query reads `accounts`, `credentials`, and optional `members`, but not `admin_users`, roles, or market grants (`apps/api/src/auth/postgres-auth.store.ts:22-52`). `AuthService.login()` therefore validates account/member status and creates tokens before any Admin-specific status or MFA decision (`apps/api/src/auth/auth.service.ts:119-166,1053-1068`).
- `resolveActor()` classifies a session as `ADMIN_USER` solely when an `admin_users` row joins to the account. It checks account status and access-token expiry/revocation, but not `admin_users.status`, role assignment, MFA, or market grants (`apps/api/src/auth/auth.service.ts:168-186`; `apps/api/src/auth/postgres-auth.store.ts:99-121`).
- `AdminGuard` only requires actor type `ADMIN_USER`; `RbacService.isAllowed()` is the current path that also requires active Admin status, active Account status, an active role assignment, a non-archived role, and a matching permission (`apps/api/src/auth/admin.guard.ts:11-29`; `apps/api/src/platform-access/rbac.service.ts:21-56`). Identity-only Admin routes therefore do not currently receive the complete eligibility gate.

### A.2 Final eligibility contract

Admin authentication reuses the canonical credential and session owner. The Admin login transaction must establish all of the following before issuing an Admin access token:

1. `accounts.status = ACTIVE`; `PENDING`, `SUSPENDED`, `LOCKED`, and `ARCHIVED` are denied.
2. Exactly one non-archived `admin_users` record exists for the Account, with `status = ACTIVE` and `archived_at IS NULL`.
3. At least one active assignment exists to one of the six controlled system-role templates. A role label supplied by the client is ignored.
4. An accepted MFA factor is enrolled and the login MFA challenge succeeds. Password success alone produces only a short-lived pre-authentication challenge, never an Admin bearer session.
5. Market grants are not credential factors. An Admin with no active market grant may complete authentication only to see a no-market bootstrap/global access-administration surface permitted by their Action Permissions; all ordinary operational reads/writes remain blocked until one active Current Admin Market is selected.

The Admin-specific login path must not use Member lifecycle status as Admin eligibility. If the same Account also has a Member record, Member suspension/closure governs Member capabilities, while Admin entry is governed by active Account + active Admin record + role + MFA. Account suspension/lock/archive remains universal and blocks all personas.

The canonical `sessions` owner also needs an immutable session purpose/actor binding (for example `ADMIN` versus `ACCOUNT`) and the bound `adminUserId` for Admin sessions. This is metadata inside the existing token/session model, not a second Admin token system. Admin login may create an `ADMIN` session only after MFA; Member/shared login creates an `ACCOUNT` session. `resolveActor()` must use that issued binding instead of dynamically turning every Account session into `ADMIN_USER` merely because an `admin_users` row exists. This prevents a dual-persona Account's Member session from inheriting Admin authority.

### A.3 Status and access-removal semantics

`admin_users` has no `INACTIVE` enum at this baseline. The final contract therefore does not invent an ambiguous fourth state: `SUSPENDED` is the reversible inactive/temporarily denied state, while `ARCHIVED` is permanent access removal. API/UI copy may say “Inactive” only as a presentation label explicitly mapped to `SUSPENDED`; stored and audited state remains canonical.

| Change                          | Login/session effect                                                           | Role/market effect                                                                | Required audit                                    |
| ------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------- |
| Account `PENDING`               | Admin login denied; no Admin session may be created                            | Existing grants remain historical only                                            | `admin.auth.denied` with safe status reason       |
| Account `SUSPENDED` or `LOCKED` | Deny login and atomically revoke every session family for the Account          | Do not delete assignments/grants                                                  | account action plus `admin.session.all_revoked`   |
| Account `ARCHIVED`              | Permanent login denial; revoke all sessions                                    | Preserve assignments/grants as history; no new assignment                         | archive and revocation evidence                   |
| Admin `ACTIVE`                  | Eligible only after role + MFA checks                                          | Effective permissions are role union subject to conflict rules                    | activation/reactivation reason and actor          |
| Admin `SUSPENDED`               | Temporary Admin denial; revoke every Admin-purpose session for the Admin       | Preserve roles/grants for reviewed reactivation                                   | status change plus revocation in one transaction  |
| Admin `ARCHIVED`                | Permanent Admin denial; revoke every Admin-purpose session; no physical delete | Revoke active roles and grants or mark them ineffective while preserving rows     | archive, role/grant disposition, revocation       |
| Last active Admin role removed  | Admin access removed; revoke every Admin-purpose session on commit             | Market grants remain historical/inert until a new controlled role is granted      | role revoke plus `ADMIN_ACCESS_REMOVED`           |
| One market grant removed        | Do not revoke unrelated sessions                                               | That market fails on next request; clear server Current Market if it was selected | grant revoke plus context invalidation            |
| All market grants removed       | Session may remain for authorized global access administration only            | Operational workspace becomes unavailable                                         | grant revocations and bootstrap unavailable state |

Admin suspension/archive, last-role removal, and exceptional MFA reset revoke all Admin-purpose sessions. Account suspension/lock/archive and password reset revoke every session for the Account. Revocation occurs in the same transaction or via a fail-closed durable outbox whose completion precedes success. Reactivation never restores revoked roles/grants/factors implicitly and always requires a fresh password + MFA login.

### A.4 Role assignment rules

- The only assignable MVP role templates are `SUPER_ADMIN`, `OPERATIONS_ADMIN`, `FINANCE_OPERATOR`, `FINANCE_APPROVER`, `KYC_REVIEWER`, and `SUPPORT_READONLY_AUDITOR`. `VIEWER` is migrated/renamed to the final Support template; no custom role or Department hierarchy exists.
- Existing `role_assignments` supports multiple active role rows and preserves assignment/revocation actors (`packages/database/schema/index.ts:616-639`). Effective permissions are the union of active assignments, then restricted by status, MFA, market grant, sensitive projection, step-up, and Maker/Checker rules.
- `SUPER_ADMIN` is exclusive and cannot be combined with another role. `FINANCE_OPERATOR` and `FINANCE_APPROVER` are mutually exclusive. `SUPPORT_READONLY_AUDITOR` cannot be combined with any write-bearing role. These assignment conflicts are checked transactionally; runtime Maker/Checker identity inequality remains mandatory even if data is malformed.
- Removing or changing assignments never mutates the permission catalog. The six system templates are versioned/controlled configuration, not user-designed roles. Super Admin is not automatically granted every newly inserted permission; permission-template changes require explicit review, step-up, reason, expected version, idempotency, and immutable audit.

### B.2 Enrollment and confirmation

1. Password-authenticated eligible Admin receives a five-minute enrollment session that cannot access Admin operations.
2. Server generates a minimum 160-bit random TOTP secret, records a pending factor, and returns an `otpauth://` URI/QR once over a no-store response. The secret never enters logs, audit JSON, analytics, URLs, browser storage, backups in plaintext, or support tools.
3. Admin confirms with a TOTP code from the authenticator. Verification accepts a 30-second time step with at most one adjacent step for clock skew, records the accepted time-step counter, and rejects replay of that counter.
4. Only successful confirmation changes the factor to `ACTIVE`. The enrollment secret/version is locked so two concurrent confirmations cannot create two primary factors.
5. Ten one-time recovery codes are generated after confirmation, displayed once, and acknowledged before enrollment completes. Only slow password hashes of normalized recovery codes are stored.
6. Enrollment, confirmation, cancellation, expiry, replay, and failure are security events. No Admin bearer session is issued until confirmation and the first login challenge complete.

### B.3 Login challenge, recovery, reset, and limits

- Password success returns a short-lived opaque `mfaChallengeId`; it does not return access/refresh tokens. The challenge is Account/Admin/factor/purpose bound, single-use, five minutes maximum, and stores only safe hashes/metadata.
- A valid TOTP completes login and creates the canonical session. Five failed verifications exhaust a challenge. Five failures within 15 minutes for the Admin/factor trigger a 15-minute MFA verification lock and a security alert; distributed rate limiting applies by Admin, challenge, and IP. Values are security configuration, not client constants.
- A recovery code may replace TOTP for one login only. It is consumed atomically, triggers notification/security audit, and forces TOTP re-enrollment before sensitive actions. Recovery code rotation requires password plus fresh TOTP step-up and invalidates every prior unused code.
- Lost-factor recovery is Admin-assisted only after identity verification under an approved operations runbook. The helper needs `admin.mfa.reset`, fresh step-up, a reason and case/ticket reference; self-reset is denied. A second authorized Super Admin must confirm the reset operationally, but this is a security recovery control and is **not** the financial Maker/Checker workflow prohibited outside MCP/iPoint.
- Reset revokes all target sessions and recovery codes, marks factors `REVOKED`, records both assisting identities and the case, and requires fresh enrollment. No one can read or export an existing TOTP secret or recovery code.

### B.4 Secret storage, encryption, and recovery

- Future factor records require encrypted secret ciphertext, random nonce/IV, authentication tag, key ID/version, algorithm, status, created/confirmed/revoked timestamps, last accepted TOTP counter, and no plaintext column.
- TOTP secrets use envelope encryption with AES-256-GCM (or an approved managed KMS equivalent), authenticated context binding the ciphertext to Account/Admin/factor ID. The master/key-encryption key lives outside Git/database and is separated from database backups. Existing voucher/transaction AES-256-GCM code is precedent only; MFA receives a domain-separated key and rotation policy.
- Recovery codes are one-way hashed with a slow password hash and individually consumed. Challenge tokens and session tokens remain opaque SHA-256 hashes following the existing auth pattern.
- Database backups contain only ciphertext/hashes. Restores require both the protected backup and separately controlled key material; key rotation retains decryption capability for active prior key versions until factors are rewrapped. Backup testing must prove restore without exposing plaintext secrets.

### B.5 Step-up contract and action map

A step-up grant is server-side, bound to Admin, canonical session, factor, action class, and target market; it is single-purpose/short-lived (maximum ten minutes), cannot outlive the session, is invalidated by role/grant/factor/session changes, and is revalidated inside the write/reveal boundary.

| Sensitive action                                             | Step-up                             | Additional control                                                                                            |
| ------------------------------------------------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Voucher plaintext reveal                                     | Required on every reveal            | `redemption.voucher.reveal`, Current Market/resource match, recorded reason, one audit per view; never cached |
| Special merchant percentage create/activate                  | Required                            | Super Admin + `merchant.special_package.manage`, explicit market, reason, immutable audit                     |
| Manual MCP/iPoint approval and execution                     | Required for Checker boundary       | Checker permission, cap routing, evidence, distinct Maker, request/target lock                                |
| Admin user status/access removal                             | Required                            | `admin.user.manage`, reason, expected version, session revocation                                             |
| Role assignment/revocation and permission-template change    | Required                            | RBAC permission, reason, conflict validation, immutable audit                                                 |
| Market grant/revoke and market registry/status configuration | Required                            | Dedicated permission, resource validation, explicit confirmation, reason                                      |
| MFA reset/recovery-code rotation                             | Required                            | Dedicated permission/self policy; target sessions/factors revoked as applicable                               |
| Raw KYC evidence or approved sensitive audit diff            | Required plus sensitive-view reason | Dedicated domain evidence permission; audit-of-view; deny-by-default projection                               |
| CSV/download/raw export request                              | **Denied regardless of step-up**    | P7-OD-14 excludes exports. Record `EXPORT_NOT_ALLOWED`; step-up can never override policy.                    |

Required security events include login challenge issued/succeeded/failed/exhausted, enrollment created/confirmed/expired, recovery consumed/rotated, factor suspended/revoked/reset, step-up issued/used/denied/expired, replay detected, rate limited, and Admin recovery approved/denied. Events contain safe actor/session/request/IP/User-Agent evidence, never factor secrets or codes.

### C.2 Final server policy

- `idleExpiresAt = min(lastActivityAt + 30 minutes, absoluteExpiresAt)`. Every authenticated request performs an atomic/tolerant activity update on the server. Reads may coalesce writes to at most once per minute, but authorization uses the authoritative stored activity time, not a browser timer.
- `absoluteExpiresAt = familyCreatedAt + 8 hours` for an Admin interactive login. Access-token expiry must never exceed it. Refresh rotation preserves `familyCreatedAt` and the same absolute ceiling.
- `familyMaxExpiresAt = familyCreatedAt + 7 days` is the outer refresh-family lifetime required by D-046. Because the interactive absolute duration is 8 hours, an Admin session cannot refresh beyond 8 hours without a new full password + MFA login; the seven-day value remains a hard family ceiling and prevents policy drift if shorter session types are later introduced.
- Existing global `AUTH_REFRESH_TTL_SECONDS=2,592,000` (30 days) cannot govern Admin families. Future Auth configuration must use explicit Admin policy values and clamp every replacement row to the original family ceilings.
- Activity is updated only after successful authentication and before/with authorization. Denied expired/revoked requests do not extend activity. Background polling/service-worker traffic does not extend an Admin session; only foreground requests carrying an explicit approved user-activity signal may do so.
- Revocation is checked on every access request and refresh. Cache use, if introduced, must be invalidated transactionally and may never delay next-request revocation.

### C.3 Session list and revocation API contract

| Method and route                           | Permission                                                                | Contract                                                                                                                                                                                          |
| ------------------------------------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/admin/sessions`               | `admin.session.read`                                                      | Current Admin's bounded sessions, derived device label, created/last-activity/idle/absolute/family expiry, IP/User-Agent evidence, current-session marker, revoked state/reason; no token hashes. |
| `DELETE /api/v1/admin/sessions/:sessionId` | `admin.session.revoke.self`; `admin.session.revoke.any` for another Admin | Revoke the selected row/family as policy requires, idempotent, reason for another Admin, cannot hide current marker.                                                                              |
| `DELETE /api/v1/admin/sessions`            | self or any permission                                                    | Revoke all target Admin Account sessions; returns counts only after commit.                                                                                                                       |

Suspension, archive, last-role removal, password reset, and MFA reset call the canonical revoke-all primitive. Refresh-token reuse revokes the entire family. A revoked session fails the next request even if its access-token expiry has not elapsed. Session create/refresh/logout/list/revoke/reuse/idle-expiry/absolute-expiry/family-expiry/suspension/password-reset events are recorded with safe Account/Admin/session/family/request/IP/User-Agent evidence.

## D. Six-role final role-to-permission matrix

### D.1 Matrix rules and legend

- `Allowed` means the role template receives the permission. `Denied` means it does not.
- `Conditional` means an owner/remediation gate, bounded projection, assignment policy, workflow state, or exceptional-operation condition must also pass.
- `Market-scoped` means Current Admin Market, active grant, and resource-market equality are all server-enforced.
- `Step-up required`, `Sensitive-view reason required`, `Maker-only`, and `Checker-only` are additional mandatory states, not substitutes for permission checks.
- `Super Admin` does not bypass market scope, sensitive reason, step-up, blocked owner gates, export denial, or same-person Maker/Checker denial.
- Every protected controller/adapter must enforce this server-side through Auth + Admin eligibility + MFA + permission + market/resource policy. Client navigation, hidden buttons, route labels, and role names are never authorization.

Role abbreviations used only in the permission-catalog tables: `SA` Super Admin, `OA` Operations Admin, `FO` Finance Operator, `FA` Finance Approver, `KR` KYC Reviewer, `SR` Support / Read-only Auditor.

## E. Canonical permission catalog

### E.1 Catalog evidence and policy

The repository has one standard seed list in `packages/database/seeds/foundation.ts:10-53`. It currently seeds 40 codes, only `SUPER_ADMIN` and `VIEWER`, grants Super Admin every permission row found in the database, and grants Viewer only codes ending in `.view` (`foundation.ts:64-93,123-143`). This creates both privilege auto-expansion and `.read` omission. The runtime decorator inventory contains 35 unique codes, including several absent from the seed. `PlatformAccessModule` registers only `AuditController`; `AccessAdministrationService` role/grant commands have no HTTP controller (`apps/api/src/platform-access/platform-access.module.ts:1-29`).

The final catalog contains **66 canonical permission codes**. Status means:

- `EXISTS_IN_SEED`: exact final code is in the foundation seed.
- `MISSING`: exact final code is absent from seed; a decorator may still use it.
- `RENAME`: an existing/requested code maps explicitly to this narrower final name.
- `DUPLICATE`: current codes/routes overlap; one canonical meaning is retained.
- `DEPRECATED`: the broad/unsafe code is not assigned by Phase 7 and must not authorize a route.

Evidence abbreviations: `F:n` = `packages/database/seeds/foundation.ts:n`; paths under `apps/api/src` are shown for decorators. Flags: `MS` market-scoped, `SU` step-up, `S` sensitive-view reason, `MO` Maker-only, `CO` Checker-only. `Gate` means assignment cannot make the capability available before its named owner/security gate.

## F. Current Admin Market architecture

### F.1 Accessible-market and selection contracts

| Method and route                      | Permission                   | Response/behavior                                                                                                                                                                                                                |
| ------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/admin/me/markets`        | Authenticated eligible Admin | Bounded active grants joined to active `markets`, returning market public ID/code/name/currency/timezone/locale, `isSelected`, grant time, and `asOf`. It never returns arbitrary/global markets and never trusts a client list. |
| `PUT /api/v1/admin/me/current-market` | `admin.market.select`        | Body contains one `marketId`, idempotency key, and expected context version. Server verifies active grant + active market, writes session-bound selection, and returns the new context/version.                                  |
| `GET /api/v1/admin/bootstrap`         | Authenticated eligible Admin | Returns actor, role templates/effective permissions, MFA/session state, accessible markets, server-selected Current Admin Market, and capability availability. It is not an authorization cache.                                 |

The selected-market representation is a nullable server-owned `currentAdminMarketId` plus `selectedAt` and an optimistic `contextVersion`, bound to the canonical session. A future forward-only Auth/Platform Access migration may add these fields to `sessions` or create a one-to-one session-context table; P7-S1C creates neither. A browser may retain only a last-selection hint. The hint, URL, `:marketId`, and `x-market-id` are never grants and are ignored until revalidated against the server session/context.

### F.2 Request enforcement

Every ordinary market-scoped request must pass, in this order:

1. Canonical session is active and within idle/absolute/family limits.
2. Account/Admin remain active, accepted MFA is bound, and required step-up remains fresh where applicable.
3. Canonical Action Permission is assigned through an active controlled role.
4. Server session has one Current Admin Market.
5. An active `market_access` row and active `markets` row still exist for that Admin/current market. Existing `RbacService.hasMarketAccess()` and partial unique grant index are reusable (`rbac.service.ts:58-77`; `schema/index.ts:641-664`).
6. Any route/header market equals the server Current Admin Market. Mismatch returns `AUTH_MARKET_CONTEXT_MISMATCH`; it never silently switches context.
7. Every resource ID is resolved server-side. Its stored market must equal the Current Admin Market. Every write DTO either omits market because the route/context owns it, or carries a target market that must equal both. Mismatch returns `RESOURCE_MARKET_MISMATCH` before mutation.
8. Owner service repeats the resource-market/state/version check inside the command transaction. Guard-only validation is insufficient for writes and sensitive reads.

Market-scoped list queries predicate by Current Admin Market before pagination. Resource-not-found and cross-market denial use a safe non-enumerating response policy. No permission may rely on client-side navigation restriction.

### F.3 Revocation, switching, and stale client selection

- Grant revocation is effective on the next request. `revokeMarketAccess()` already updates the grant and appends audit in one transaction (`access-administration.service.ts:109-143`); the final command also invalidates matching session contexts and emits a context event before success.
- Market switch audit records Admin/account/session, from/to market, result/denial reason, UTC time, market-local display time, request/correlation ID, IP, User-Agent/device label, and context version. It records activity but never grants access.
- If local storage, a deep link, or a restored browser tab names a market that is no longer granted/active, bootstrap does not adopt it. The server clears/returns no selection and responds `ADMIN_MARKET_SELECTION_REQUIRED` with the authorized list. The UI removes the hint and requires explicit reselection.
- If a grant is revoked during an open page, the next API call returns `AUTH_MARKET_ACCESS_DENIED`; no stale read, write retry, service-worker replay, or automatic fallback to another market is allowed.

### F.4 No-global-write and currency rules

- Every write, including Super Admin operations, targets exactly one explicit market. There is no wildcard, `ALL`, omitted-market fallback, browser fan-out, bulk replication, or global operational write mode.
- Market registry identity actions may be globally listed only with their dedicated global permission, but creating/changing a market remains a single target-resource command with step-up, reason, dependency checks, idempotency, and audit.
- Monetary, MCP, iPoint, wallet, commission, redemption, and rate values remain grouped by market and currency code. No cross-currency total, silent conversion, Malaysia default, or “platform total” is permitted. Basic reports return separate market/currency buckets and `Unavailable` for blocked inputs.
- Read-only global overview remains deferred under P7-OD-02. The accessible-market endpoint is not a global dashboard and does not authorize aggregation.
